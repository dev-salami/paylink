# x402 on PayLink

Premium agent actions are HTTP resources:

| Resource | Route | Default price |
| --- | --- | --- |
| Branded PDF invoice | `POST /api/x402/pdf?invoice=<id>` | 0.25 USDC |
| Smart reminder email | `POST /api/x402/reminder?invoice=<id>` | 0.05 USDC |

`/api/x402/pdf`, `/api/x402/reminder`, and `/api/x402/lab` are public so a judge can request a 402 without the merchant access code. The dashboard, agent, wallet, and settings stay behind `PAYLINK_ACCESS_CODE`.

Prices, the total cap, the per-call cap, and the approval threshold come from the environment on a fresh store, then from the wallet page.

## Protocol

This is x402 V2 on Solana devnet. V1 header names (`X-PAYMENT`) and the network name `solana-devnet` are not used.

| Step | What happens |
| --- | --- |
| Request | No `PAYMENT-SIGNATURE` header. The route returns **402** with a `PAYMENT-REQUIRED` header and a JSON body. The body is a `PaymentRequired` object: `x402Version: 2`, `accepts[]` with scheme `exact`, network `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`, atomic amount, USDC mint, merchant `payTo`, and `extra.memo` set to the quote id. |
| Sign | The agent wallet (server-side) builds a partially signed SPL `TransferChecked` with the official `@x402/svm` exact client. The merchant key is the fee payer. |
| Retry | The same request is sent with `PAYMENT-SIGNATURE` set to the base64 `PaymentPayload`. |
| Verify | `@x402/svm` checks the transfer outcome: amount, mint, recipient associated token account, memo, fee-payer isolation, and that the authorization is not expired. |
| Settle | The facilitator co-signs as fee payer and submits. The response carries `PAYMENT-RESPONSE` with the devnet signature. |
| Deliver | The PDF bytes, or the reminder email, are returned only after settlement. |

The agent chat shows that sequence as request, settle, and deliver. The activity page can also fetch a live 402 without paying.

## Why settlement is in-process

`@x402/core` and `@x402/svm` 2.29.0 are the resource server, the client, and the facilitator. The facilitator scheme registered in this app is the reference `ExactSvmScheme`. It verifies and settles on devnet with the merchant key sponsoring the SOL fee.

A remote facilitator is optional. Set `X402_FACILITATOR_URL` (for example `https://x402.org/facilitator` or a PayAI endpoint). On boot the app asks `/supported`. If that call fails, or devnet is not advertised, it keeps the in-process facilitator instead of pretending a remote one is up.

The in-process path is the one the demo uses, for two reasons:

- A public facilitator can be down during a demo, and a network error must not be treated as proof of payment.
- A public facilitator will not sponsor fees for a practice mint created by `pnpm devnet -- --mock-usdc`. The reference scheme will, because the merchant key is the fee payer.

The reference facilitator already refuses a second settle of the same payload (`duplicate_settlement` / its settlement cache) and remembers a broadcast whose confirmation was lost so a retry does not build a second transaction.

## Budget before any signature

The agent wallet checks three rules before it signs. A refusal here means no transaction is created.

| Rule | Default | Result |
| --- | --- | --- |
| Per-call cap | 0.50 USDC | `over_cap` |
| Total cap | 5 USDC | `insufficient_budget` |
| Approve above | 0.10 USDC | The chat shows the 402 and waits. Decline sends nothing. |

A reminder at 0.05 USDC is under the line and pays immediately. A PDF at 0.25 USDC waits for approval. Both still have to pass the caps.

## Failure table

These are the cases the activity page runs, and the cases the unit tests lock in. "Charged" means a new debit of the agent budget on that attempt.

| Case | Where it is decided | HTTP | Charged | What you should see |
| --- | --- | --- | --- | --- |
| Insufficient budget | Agent policy, before sign | — | No | The chat explains the remaining balance. The wallet is not asked to sign. |
| Over the per-call cap | Agent policy, before sign | — | No | The call is refused even if you have total budget left. |
| Price mismatch | Resource server compares the signed `accepted` requirements with the stored quote | 402 | No | A proof whose amount, recipient, or memo does not match the quote is rejected before verify. |
| Underpaid | Quote check, or the observed transfer amount is below the quote. Invoice payments use the same word when `validateTransfer` reports `amount not transferred`. | 402, or invoice status `underpaid` | No | The resource stays locked. An invoice shows the short amount and keeps the signature. |
| Wrong mint | Quote asset check, facilitator reason, or token balance delta on an invoice | 402, or invoice stays `pending` with a wrong-mint banner | No | A different SPL mint is not accepted as USDC. |
| Replayed proof | Settlement record says this proof id was already delivered | 409 | No | The old signature is returned. Verify and settle are not called again. |
| Expired quote | `expiresAt` on the quote, or a facilitator blockhash expiry | 402 | No | The client must request a fresh 402. Nothing is settled. |
| RPC or facilitator down | Verify or settle throws, or returns pending confirmation | 503 | No | Fail closed. If a signature was already broadcast, it is stored as pending and a retry looks up that signature instead of paying again. |
| Paid, delivery failed | Settle succeeded, then the PDF or mailer threw | 502 | Yes, once | The spend log shows `delivery_failed`. Retrying the same `PAYMENT-SIGNATURE` delivers the resource and does not settle a second time. |

Send `x-paylink-fault: facilitator` or `x-paylink-fault: delivery` on a real retry to force the last two paths against the HTTP route. The activity lab does not touch devnet. It calls the same policy functions the route uses.

Invoice payments that are short or on the wrong mint are not x402 calls. They are classified by `findReference`, `validateTransfer`, and the token balance delta, then shown on the invoice and the pay page. `pnpm pay -- --invoice <id> --amount 10` is the short-payment drill.

## Idempotency

- A quote id is the memo inside the payment requirements. That id is the proof id.
- The settlement record is written before the HTTP response returns.
- `charged` is recorded only on the first successful settle.
- A delivered proof cannot pay for a second copy.
- A settled-but-undelivered proof skips settle on retry.
- A pending signature is reused and does not add a debit.
- The budget moves when a settle is confirmed, including when delivery then fails, and a later retry of that proof does not add a second debit.
